# 决策备忘录：COUNT_FULL 等价机制的正确落点是检索完备性，不是上下文注入

日期：2026-10-24 · 依据：`docs/evidence/product-gap-forensics/` 修正版重跑（records-rev1.json / summary-rev1.json，2026-10-23，本地无 API，逐题观测与 2026-10-02 原跑零漂移） · 池：LongMemEval multi-session 133 题中 17 道 harness 对/product 错的差距题（产品基线 102/133 = 0.7669）

## 修正后的归因（详见 manifest `measurement_revision`）

| 阶段 | 题数 | 说明 |
| --- | --- | --- |
| retrieval（计数题按全枚举口径） | **15** | 全部为 counting-intent（关键词启发式，非真值） |
| context | 1 | 非计数题，2 位数字答案确实不在装配上下文中 |
| answerer | 1 | 与原跑一致 |
| write | 0 | 原文层零丢失结论不变 |

计数题的会话级覆盖量化（15 题）：gold session 共 **48** 个，top-24（orchestrated + paragraph-primary）只覆盖 **15** 个 = **31.3%**；**6/15 题零覆盖**，9/15 部分覆盖。

## 对 COUNT_FULL 原方向的修正

原 manifest 的可行动结论是"计数题把完整候选会话**前插进上下文**"。修正口径下该结论不成立：**上下文注入无法注入检索从未选出的会话**。6 题零覆盖、平均覆盖 31% 意味着瓶颈在**候选组合的完备性**，不在装配。

因此产品化方向应为：**计数/聚合意图查询改变检索组合**——对该类查询按会话单元做完整枚举（例如会话分区检索腿/聚合腿，枚举出候选全集），其后再做完整会话的上下文装配（原 COUNT_FULL 的装配部分退化为该组合的下游步骤）。装配与组合两件事都做，但组合是必要条件。

这恰好落在"暂停新增检索组件"约束的裁决线上：**冻结维持**，直到按 P0 统计门（逐题配对、both-judged 子集、与 Raw-RAG 对照同读者同预算）在默认产品路径上通过 A/B。

## 上限重算（从 rev1 逐题行直接推导）

- 仅翻转 15 道计数题：(102+15)/133 = **117/133 ≈ 0.880**（与旧 0.8796 数值相同纯属基数巧合——旧值的"上下文装配"推导路径无效，本值从修正归因重推）。
- 翻转全部 17 题：119/133 ≈ **0.895**（含 1 道 context + 1 道 answerer，二者无检索方案可救，不应计入检索侧预期收益）。
- 诚实例行：上限假设每道翻转题都判对；harness 曾用同一 answerer 判对这 17 题，从上方约束该假设，但产品路径 answerer 未重验。

## 验收框架（进入实现前固定）

1. 对照组：默认非编排 / orchestrated top-24 / 计数组合变体 / **Raw-RAG 基线**（纯原文 BM25，同库同预算）/ oracle 全覆盖。
2. 指标：会话级 any/full 覆盖率（先决指标）+ 最终答案正确率（同 answerer、同 judge、逐题配对、both-judged 子集）。
3. 门：计数组合变体相对 orchestrated 与 Raw-RAG 基线的配对增益显著、且非计数题无回归，才可离开实验开关。
4. 口径纪律：counting_intent 启发式须双标注（启发式判定 + 人工抽检）；单跑确定性检索无方差，答案端方差按既有 paired 协议。

## 边界

- 本备忘录只重定方向与上限，不构成开工批准；实现属 P3，前置 P0 统计与基线矩阵。
- 池仅 17 道差距题（非 133 全池），覆盖率数字不可外推到全池。

## 基线实测（2026-10-24）

验收框架第 1 条的四对照臂（计数组合变体除外）已在本地矩阵落地：`scripts/product_retrieval_baseline.py`，133 道 multi-session 题、每题独立新库只种自己的 haystack、四组合查同一语料、top-24，会话级 any/full 覆盖按计数意图分层（关键词启发式）。证据与局限见 `docs/evidence/product-retrieval-baseline/manifest.md`。

| 组合 | any/计数 | full/计数 | any/非计数 | full/非计数 |
| --- | --- | --- | --- | --- |
| default | 50/99 = 0.5051 | 7/99 = 0.0707 | 21/34 = 0.6176 | 3/34 = 0.0882 |
| orchestrated | 50/99 = 0.5051 | 7/99 = 0.0707 | 21/34 = 0.6176 | 3/34 = 0.0882 |
| parity | 96/99 = 0.9697 | 40/99 = 0.4040 | 34/34 = 1.0000 | 16/34 = 0.4706 |
| rawrag（Raw-RAG 对照） | 98/99 = 0.9899 | **87/99 = 0.8788** | 34/34 = 1.0000 | 32/34 = 0.9412 |

解读：**Raw-RAG 对照的计数题 full 覆盖比 orchestrated/parity 都高**——0.8788 对 orchestrated 的 0.0707 高 80.8 个百分点、对 parity 的 0.4040 高 47.5 个百分点（87 题对 7 题对 40 题全枚举成功）。这**支持**本备忘录"计数题需要检索组合完备性"的方向：同一语料、同一 top-24 下，仅以会话为排序单元对原文跑 BM25 就能让 87.8% 的计数题把全部 gold 会话排进 top-24，说明 31.3% 平均覆盖的瓶颈不在"gold 会话排不出来"，而在产品栈组合没有会话级枚举腿——完备枚举天花板可达，且不需要新增检索组件（Raw-RAG 腿本身就是组合变更）。另两点只陈述数字：default 与 orchestrated 四格逐位相同且 rows.json 逐题 any/full/hits 完全一致（无增强 LLM 时 orchestrated 退化为 fail-closed 单查询扇出，本矩阵二者的零差只是本地无 LLM 差异，不可外推）；非计数题上 parity 与 rawrag 的 any 覆盖同为 1.0000，full 差距（0.4706 vs 0.9412）同样指向枚举单元而非意图分层。以上均为检索级指标，无答案正确率；单次运行；counting 为关键词启发式（99/133）；覆盖解析规则沿用 gap_forensics（服务组合经段落前缀映射或 80 字符正文包含判定，rawrag 直接按会话 id，排序单元不同正是对照要测的对象）。
